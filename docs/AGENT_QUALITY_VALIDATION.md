# Agent Quality Validation Guide

이 문서는 `AGENTS.md`의 사용자-visible 품질 검증 규칙을 구체화한다.
물리/시뮬레이션, 렌더링/VFX, 카메라/추적, 입력, 상호작용 UI처럼 **실제 실행 결과의 체감 품질이 작업 목표에 포함되는 변경**에 적용한다.

이 문서는 제품 동작을 정의하는 소스 코드가 아니라 AI 에이전트의 작업·검증 절차다. 작업별 세부 목표와 수치 기준은 해당 Issue/PR/사용자 요청에서 정하고, 여기에는 반복해서 적용할 검증 절차만 둔다.

## 1. 완료의 의미

자동 테스트, 타입 검사, 빌드, CI 통과는 필요한 기술 검증이지만 사용자-visible 품질의 최종 승인과 동일하지 않다.

사용자-visible 품질 작업은 다음 두 상태를 구분한다.

- **기술 검증 완료**: 구현, 회귀 테스트, 빌드/CI, 실제 실행 확인 등 에이전트가 수행할 수 있는 검증을 통과한 상태
- **사용자 결과 확인 완료**: 사용자가 중요하게 보는 실제 결과물까지 확인되어 요청한 체감 품질이 충족된 상태

사용자 확인이 아직 필요한데 `완료`, `최종`, `해결됨`이라고 단정하지 않는다.

## 2. 작업 시작 전 — 문제와 기준을 먼저 고정

구현 전에 다음을 확인한다.

1. **문제의 실제 계층**을 구분한다.
   - physics/state: 위치, 속도, 충돌, 보존량, 상태 전이 등 실제 시뮬레이션 값
   - presentation: 렌더링, VFX, 보간, 화면상의 강조
   - interaction/UI: 입력, 카메라, 패널, 사용자 피드백
2. 현재 `main`에서 문제를 재현하거나 기존 결과를 확인해 **baseline**을 잡는다.
3. 사용자가 영상/이미지/재현 절차를 제공했다면 그것을 우선 기준으로 삼는다.
4. "개선", "자연스럽게", "현실적으로", "덜 어색하게"처럼 정성적인 요청은 구현 전에 관찰 가능한 acceptance criteria로 풀어 쓴다.

Acceptance criteria는 작업별로 정한다. 검증 근거 없이 저장소 공통 규칙에 임의의 숫자 임계값을 영구화하지 않는다.

## 3. 구현 계층을 속이지 않는다

원인이 실제 physics/state에 있는데 renderer clone, CSS, 화면 offset, VFX 등 presentation-only 변경으로 가려 놓은 경우 이를 근본 문제 해결로 보고하면 안 된다.

presentation-only 처리가 적절한 경우는 다음 중 하나다.

- 사용자 요청 자체가 시각적 연출 개선인 경우
- 실제 상태를 변경하면 물리 정확성이나 기존 계약을 훼손하는 경우
- presentation layer가 문제의 실제 원인임을 확인한 경우

presentation-only 접근을 사용했다면 PR과 완료 보고에서 다음을 명시한다.

- 실제 simulation state가 변경됐는지 여부
- 화면 표현만 변경됐는지 여부
- 원래 요청을 충족한다고 판단한 근거

## 4. 검증은 세 층으로 수행한다

### A. Correctness

변경 성격에 맞는 자동 검증을 수행한다.

- 회귀 테스트
- 타입 검사
- 빌드
- CI
- 물리 보존량/불변식 검증 등

자동 검증이 통과해도 실제 결과 확인을 생략할 근거가 되지 않는다.

### B. Runtime result

실제 앱/시뮬레이션을 실행해 요청한 현상을 직접 확인한다.

가능하면 다음 조건을 고정한다.

- 초기 상태 또는 seed
- 카메라/줌
- 시간 배속 또는 timestep 조건
- 입력 순서
- 관찰 시점

사용자가 특정 영상이나 재현 절차를 기준으로 문제를 제기했다면 동일하거나 충분히 동등한 조건으로 재검증한다.

### C. A/B comparison

기존 동작을 "개선"하는 작업은 가능하면 동일 조건의 baseline과 변경 결과를 직접 비교한다.

비교 시 다음을 확인한다.

- 목표로 한 문제가 실제로 줄었는가
- 새로운 부작용이 생기지 않았는가
- 다른 계층의 트릭으로 문제를 단순히 가린 것은 아닌가
- 개선 폭이 사용자-visible한가

새 결과만 보고 "좋아졌다"고 판정하지 않는다.

## 5. 영상·이미지가 핵심 증거인 작업

시각 품질이 핵심인 작업에서는 코드 diff나 CI 결과만으로 승인하지 않는다.

가능한 환경에서는 대표 시나리오의 스크린샷/영상/브라우저 회귀 결과 등 **실행 증거**를 남긴다. 자동 캡처가 없으면 수동 실행 검증 결과와 재현 조건을 PR에 기록한다.

사용자가 실제 녹화 결과를 제공한 경우 그 결과에서 드러난 문제를 acceptance criteria에 반영하고, 수정 후 같은 종류의 결과를 다시 확인한다.

## 6. 병렬 작업과 integration

강하게 결합된 기능을 여러 PR/브랜치로 병렬화할 수는 있지만 각 병렬 PR은 **부분 작업**으로 취급한다.

예를 들어 physics → collision resolution → fragment motion → VFX → observer UI처럼 한 사용자 경험을 구성하는 변경은 개별 PR이 모두 성공해도 전체 경험이 성공했다고 볼 수 없다.

최종 integration 담당자는 반드시 다음을 다시 수행한다.

1. 최신 `main` 기준으로 통합 상태 확인
2. 각 부분 변경의 의도와 실제 구현 계층 확인
3. 충돌/중복/상호작용 문제 확인
4. 전체 acceptance criteria를 end-to-end로 재검증
5. 실제 실행 결과를 다시 확인
6. 필요한 경우 통합 브랜치에서 추가 조정

개별 PR의 CI 통과 또는 리뷰 결과를 최종 integration의 품질 검증으로 대체하지 않는다.

## 7. 에이전트가 임의로 성공 기준을 낮추지 않는다

작업 중 구현 난이도나 기존 구조 때문에 처음 의도보다 약한 해결책을 선택하게 되면 조용히 완료 기준을 낮추지 않는다.

다음 중 하나로 처리한다.

- 원래 acceptance criteria를 충족하도록 추가 수정
- 기술적으로 충족하지 못한 항목을 명시하고 미완료로 보고
- 사용자의 명시적 동의가 있을 때만 scope/기준 변경

"테스트가 통과하므로 충분하다", "현재 구조상 이 정도가 최선이다" 같은 추정만으로 사용자 목표를 축소하지 않는다.

## 8. PR에 남겨야 할 검증 정보

사용자-visible 품질 변경 PR에는 가능한 범위에서 다음을 기록한다.

- 원래 문제와 baseline
- 작업별 acceptance criteria
- 실제 수정 계층(physics/state, presentation, UI 등)
- 실행한 자동 테스트
- 실제 실행 검증 조건과 결과
- 개선 작업이면 baseline 대비 차이
- 남은 제한 또는 사용자 확인이 필요한 항목

## 9. 완료 보고 금지 사례

다음 중 하나라도 해당하면 사용자-visible 품질 작업을 최종 완료로 보고하지 않는다.

- 빌드/CI만 확인하고 실제 실행 결과를 확인하지 않음
- 사용자가 제시한 재현 조건을 무시함
- 근본 원인을 다른 시각 계층에서 가리기만 했는데 이를 근본 해결로 표현함
- 병렬 PR 각각만 검증하고 통합 결과를 end-to-end로 확인하지 않음
- 개선 전 baseline 없이 새 결과만 보고 정성적으로 성공 판정함
- acceptance criteria 중 충족하지 못한 항목을 보고에서 누락함

## 10. 기본 원칙

품질 보증의 기준은 에이전트의 "괜찮아 보인다"는 판단이 아니다.

**사전에 정한 작업별 acceptance criteria + 자동 correctness 검증 + 실제 실행 결과 + 필요한 A/B 비교**를 근거로 판단한다.
